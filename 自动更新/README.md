# FileView 自动更新 —— 操作手册

> 目标：以后 FileView 有新版时，你不用再手动"卸载 → 上传 → 安装"，由 NAS 自己完成。

---

## 一、先说清楚：飞牛那个「自动更新应用」开关对本应用**无效**

应用设置里确实有个「自动更新应用」开关，但它只对**在应用中心上架**的应用有效。

依据（官方文档，已全站核对）：

| 查了什么 | 结论 |
|---|---|
| manifest 字段清单 | **没有任何"更新源 / 更新地址 / 更新通道"字段**，只有一个 `changelog`（更新说明，用于在更新界面展示文字） |
| 《上架应用》 | 更新是通过**应用中心分发**的；要能自动更新，得先上架（开发者先锋交流群提交） |
| 《appcenter-cli》 | 官方提供了命令行安装入口 `appcenter-cli install-fpk myapp.fpk --env config.env` —— **这是"可脚本化更新"的官方抓手** |

我们是手动安装的 `source=thirdparty` 包，飞牛不知道去哪里查新版本，所以开关打开也没用。

**两条可选路线：**

| 路线 | 可行性 | 说明 |
|---|---|---|
| 上架应用中心 | ❌ 不建议 | 本包是 BaseMetas FileView 的二次打包，上架涉及原作者版权与长期维护责任；本项目定位是个人自用/小范围分发 |
| **自建发布点 + 计划任务** | ✅ **推荐** | 用官方 `appcenter-cli install-fpk`，本目录的脚本已写好 |

## 二、包版本号规则（决定"能不能就地升级"）

包版本与预览引擎版本**完全脱钩，从低处起算**，留足递增空间：

| 包版本 | 对应引擎 | 什么时候用 |
|---|---|---|
| **0.5.8** | **1.5.2** | **当前版本**。命名规则：引擎 1.5.2 → 包版本 0.5.2 起算（首位降 1，便于一眼对上引擎） |
| 0.5.9 / 0.5.10 … | 1.5.2 | 只改配置、图标、nginx → 末位 +1 |
| 0.6.0 | 1.6.0 | 引擎升级时跟着抬（引擎 1.6.0 → 包 0.6.0），同时改 compose 的 `image` tag |

**为什么要递增**：飞牛判断"升级安装"靠版本号递增。版本号不变时同版本**不允许覆盖安装**（这也是之前每次都得先卸载的原因）；递增后可以**就地升级**，走包里的 `cmd/upgrade_init` / `upgrade_callback`，不用卸载。

**为什么从 0.5.2 起算**：这样外壳版本和引擎版本走两条线，以后外壳改很多次也不会撞上引擎的版本号，永远有递增空间。

## 三、搭建发布点（一次性）

准备一个能通过 HTTP 访问的目录，放两个文件：

```
你的发布点/
├── version.txt                    ← 纯文本，内容就是版本号，例如：0.5.8
└── basemetas-fileview.fpk         ← 新版的安装包
```

要点：

- **`version.txt` 的内容不要有 BOM、不要有中文、结尾换行可有可无**（脚本会去掉空白）。写错会让脚本反复"发现新版本"。
- 发布点可以是任意静态服务：飞牛自带的 Web 服务、对象存储、你自己的反向代理目录都行。
- 发布点可以是任意静态服务：飞牛自带的 Web 服务、对象存储、你自己的反向代理目录都行；直接用本仓库 Release 资产（公开可匿名下载）也可以。
- 若发布点在内网，脚本本来就跑在 NAS 本机，用内网地址最省事、也最安全。

## 四、准备向导答案文件（一次性）

自动安装是非交互的，**必须**把安装向导的答案先准备好，否则会卡在向导。

```bash
mkdir -p /vol1/1000/docker/fileview-update
cat > /vol1/1000/docker/fileview-update/config.env <<'EOF'
wizard_volumes=auto
EOF
```

- `wizard_volumes` 是安装向导里唯一的字段（允许预览的存储卷）。**改这里等于改挂载卷**。
  - `auto`（0.5.6 起默认，推荐）：安装时自动探测 `/proc/mounts` 里所有 `/volN`，以后新加硬盘不用改设置。
  - 也可以显式写逗号分隔的卷名，如 `/vol1,/vol2,/vol3`。
- 字段名必须与 `fpk/basemetas-fileview/wizard/install` 里的 `field` 完全一致。

## 五、部署脚本并首次手动验证

```bash
mkdir -p /vol1/1000/docker/fileview-update
# 把本目录的 auto-update.sh 传上去，然后：
chmod +x /vol1/1000/docker/fileview-update/auto-update.sh

# 先手动跑一次（务必先手动跑，确认日志无误再挂计划任务）
/vol1/1000/docker/fileview-update/auto-update.sh
tail -n 40 /vol1/1000/docker/fileview-update/auto-update.log
```

可用环境变量覆盖默认值（不改脚本文件）：

```bash
UPDATE_BASE="http://192.168.1.10/pkgs/fileview" \
WORKDIR="/vol1/1000/docker/fileview-update" \
/vol1/1000/docker/fileview-update/auto-update.sh
```

脚本做事的顺序：取远端版本 → 取本机版本 → 比对 → 下载并用 `1f 8b` 魔数校验 → `appcenter-cli install-fpk --env` → 记录版本状态。任一步失败都会写日志并退出，**不会留下半成品**。

### 两点待验证

1. **`appcenter-cli list` 的输出格式未知**，脚本用宽松正则（`grep -oE '[0-9]+(\.[0-9]+)+'`）提取版本号；解析不出来时会退回状态文件 `last-installed-version`。第一次手动跑时看一眼日志里的「本机版本」对不对。
2. **`appcenter-cli install-fpk` 对已安装应用的行为未验证**（是走升级、还是报错拒绝）。如果不走升级，就改成"先 `appcenter-cli stop` + 卸载再装"，或者在飞牛界面里点升级。
3. **升级会覆盖 `docker-compose.yaml`**：框架把新的 `app.tgz` 释放到 `${TRIM_APPDEST}` 时，会把挂载段顶回模板里的 `/vol1`、`/vol2`。0.5.8 起 `cmd/upgrade_callback` 与 `cmd/main start` 会自动重写回来，所以自动更新不会再「更新一次丢一个盘」。升级完可以用 `bash tools/fv-doctor.sh` 确认各卷都在容器里。

## 六、挂到飞牛「计划任务」

系统设置 → **计划任务** → 新增 → 自定义脚本：

| 项 | 值 |
|---|---|
| 任务名称 | FileView 自动更新 |
| 执行周期 | 每天 04:00（或每周一次） |
| 脚本内容 | `/vol1/1000/docker/fileview-update/auto-update.sh` |

建议**每周一次**就好。这个包不是高频更新的东西，而且每次更新都会短暂重启容器。

> 💡 想先收到通知再决定？把脚本第 5 步（安装那一段）注释掉，只保留"检查+下载"，日志里会写明发现了哪个新版本。

## 七、另一种"自动更新"：引擎镜像

真正会持续变新的其实是 **FileView 的 Docker 镜像**，而不是我们的 .fpk 外壳。

当前 compose 里写的是固定 tag（`basemetas/fileview:1.5.2`），这是**刻意的**：

- 固定 tag → 结果可复现，出问题能对得上版本，符合工程环境的习惯；
- 改成 `latest` + 定时 `docker compose pull` 虽然能"自动跟进"，但**任何一次上游破坏性改动都会在半夜自动生效**，且和你记录在案的版本号对不上。

**建议保持固定 tag**，引擎升级走"改 tag → 打新包 → 让上面的脚本装"。如需让镜像自动跟进，可另配一份 `docker compose pull` 的计划任务脚本。

## 八、小结

| 你想要的 | 结论 |
|---|---|
| 打开飞牛那个「自动更新应用」开关就行 | ❌ 对手动安装的包无效（官方只给应用中心上架的应用做更新检查） |
| 半自动/自动更新 | ✅ 用本目录的脚本 + 计划任务，基于官方 `appcenter-cli install-fpk` |
| 每次都要先卸载 | ✅ 已通过版本号规则解决（`0.5.x` 起的升级安装） |
